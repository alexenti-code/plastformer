## 2. Проверенный механизм: как Φ живёт в файле

Это **главный технический результат 11.09.2026**. Проверено на копии настоящего шарда.

**Что проверено и работает:**

1. **Φ — хвостовой регион файла,** а не отдельный тензор в шапке. Обычные тензоры кончаются на известном смещении; за ними дописываются байты Φ. Шапка safetensors при этом не меняется.
2. **`mx.load` читает файл с хвостом** — вернул все 286 тензоров, хвост не мешает.
3. **`mlx_lm.load` грузит модель с хвостом** — загрузка 4,1 с, 6701 МБ, генерация работает.
4. **Строгая загрузка проходит** — `load_model(strict=True)` не падает от лишнего хвоста.
5. **Запись в хвост на месте:** записал строку на смещении, прочитал обратно — совпало; размер файла не изменился; остальные тензоры не тронуты.

**Что НЕ работает и почему так делать нельзя:**

- **Добавлять Φ тензором в шапку safetensors — нельзя.** Проверено: `load_model` падает с «Received 1 parameters not in model: phi1.records» и грузиться отказывается.
- **Вывод:** Φ живёт как хвостовой регион, модель о нём не знает. Это правильно и по канону: Φ — часть файла, но её читает и пишет код, а не веса.

**Как вычисляется смещение Φ:** прочитать шапку safetensors (8 байт длины + JSON), найти максимум `data_offsets[1]` по всем тензорам; смещение Φ = 8 + длина шапки + этот максимум. Для шарда 2 ядра это дало смещение 1 347 400 832.

**Формат хвоста Φ (предлагаемый, 4 КБ шапки + область записей):**

    смещение Φ + 0      : 4 байта длины, затем JSON-шапка
    JSON: {"magic":"PLASTPHI","v":1,"rec":1001,"n1":1298701,"n2":199800,"tick":0,
           "bytes_phi1":1298701001,"bytes_phi2":199800001}
    далее Φ1: n1 записей по rec байт
    далее Φ2: n2 записей по rec байт

**Формат одной записи (1 001 байт):**

| Смещение | Поле | Байт |
|---|---|---|
| 0 | вектор содержания | 1 920 (3840 чисел по полбайта) |
| 1920 | пять амплитуд, float32 | 20 |
| 1940 | valid_time, int64 | 8 |
| 1948 | record_tick, int32 | 4 |
| 1952 | источник (user / own_derivation / tool_result) | 1 |
| 1953 | номер записи, int64 | 8 |
| 1961 | резерв выравнивания | 40 |
| **итого** | | **1001** |

**Найдено важное (в плане это не было учтено):**

1. **Ядро требует шаблон чата.** Если подать простую строку, модель отвечает мусором — выдаёт ряд подчёркиваний. Через `tokenizer.apply_chat_template(...)` ответ связный и на русском. **В прогоне экзамена (этап 7) обязательно применять шаблон чата.**
2. **Модель печатает блок размышлений** — в ответе видно `<|channel>thought`. При замерах и оценке ответов этот блок надо отрезать отдельно, иначе он попадёт в метрики.
3. **Длина 1024 в проходе взята с запасом:** самые длинные записи материала — 528 токенов. 1024 оставляем, чтобы не резать.

Гейт пройден: ядро грузится и отвечает, материал цел, хвост Φ свободен. Можно переходить к этапу 2.

### Этап 3. Слияние адаптера в ядро (минуты)

Проблема: проход даёт отдельный файл адаптера, а изделие — один файл. Сливать надо **на полных числах**, потому что слияние поверх сжатых 4-битных весов уже один раз сломало модель (брак a0).

Что делать: распаковка ядра в полный вес по слоям с записью на диск, прибавление добавок, сохранение, обратное сжатие в 4 бита.

Порядок:
1. Де-квантовать ядро послойно (пик памяти — один слой, не весь файл).
2. Прибавить добавки адаптера к полным числам.
3. Сохранить один файл во временную папку.
4. Сжать обратно в 4 бита.
5. Проверить одной генерацией.

**Риск, который надо назвать честно:** обратное сжатие 16 → 4 бита никем не измерялось. Это может испортить веса так же, как брак a0. Проверка после сжатия — одна генерация и сравнение с базовым ответом.

**Если сжатие испортит модель** — оставить ядро в полном весе (около 24 ГБ) и переносить сборку на машину с большей памятью. Это заранее известный выход.

### Этап 5. Код работы с Φ (написать заново, ~300 строк)

## 4. Что менять при провале — таблица диагностики

| Что сломалось | Наиболее вероятная причина | Что менять |
|---|---|---|
| Модель не грузится | испорчено слияние (шаг 4 этапа 3) | не сжимать обратно в 4 бита; оставить полный вес |
| Модель отвечает рядом подчёркиваний или мусором | промпт подан простой строкой, без шаблона чата | подать через `apply_chat_template`; это не поломка модели |
| Модель грузится, но отвечает бессвязно (и через шаблон тоже) | деградация от прохода Инструкции | уменьшить итерации (300 → 150), ранг 8 → 4 |
| Акты не выпускаются | мало грамматики в материале | поднять долю грамматики 15,5 % → 20 % и перегенерировать материал |
| Акты выпускаются, но память не работает | ошибка в коде Φ, а не в модели | проверить смещение Φ и шапку; прогнать тест записи-чтения отдельно |
| Памяти не хватает | Φ или окно слишком велики | уменьшить Φ (1,5 → 0,8 ГБ) или окно (8к → 4к) |
| Φ заполнилась за прогон | счёт идёт по токенам, а не по актам | пересчитать размер; для 200 запросов хватает 601 МБ в полном виде |
| Записи Φ не читаются | вектор не декодируется | для образца читать содержание из служебной области, а не из вектора; назвать это ограничением |

## 5. Что этот план НЕ решает (честная граница)

- **Запись во время генерации.** Проверена запись в файл на месте, но не из самого процесса модели во время работы.
- **Декодирование вектора Φ обратно в текст.** Для образца не делается; чтение идёт по служебной копии содержания.
- **Вытеснение при заполнении Φ1.** Механика описана, поведение не наблюдалось.
- **Сжатие вектора до 512 чисел.** Обсуждалось как экономия, но качество чтения не измерялось; для образца берётся половинное хранение 1920 чисел, оно безопаснее.
- **Генератор материала v03.** В репозитории нет; если материал придётся пересобрать, генератор надо написать заново.
