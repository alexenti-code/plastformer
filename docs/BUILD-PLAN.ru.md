## 1. Что строится

**Модель, у которой память лежит в её же весах, стареет по физике и возвращается в восприятие.**

**Три свойства, из которых следует вся архитектура:**

1. **Пишется на каждом акте, немедленно, с попаданием на диск.** Запись — часть работы, не сохранение.
2. **Затухание вычисляется, не хранится.** Хранится начальная амплитуда и тик.
3. **Файл один.** Тело одно.

**Проверка готовности:** стереть историю диалога → задать вопрос о прошлом → получить верный ответ из Φ, при этом в файле памяти **настоящие векторы**, а старые записи **тише** новых.

## 2. Четыре решения, без которых нельзя строить

| # | Вопрос | Варианты | Моя рекомендация |
|---|---|---|---|
| **1** | **Закон затухания** | (а) как в обучении: **одна τ на слой**; (б) как в каноне: сумма по пяти τ; (в) как в изделии: максимум | **(а)** — модель училась именно на нём; канон и материал потом свести |

| **4** | **Спячка** | (а) **след разрыва при пробуждении**; (б) разрыв не событие | **(а)** — канон прямо говорит «пробуждение — записываемое событие» |

## 3. Технологическая карта: ЧТО происходит и КОГДА

Все процессы изделия. Для каждого: **кто делает, когда, что на диске до и после**.

### 3.1. Общая карта жизни

```
[однократно]  СБОРКА          -> файл A = (K, Φ)
[однократно]  ПЕРЕДАЧА        -> файл у владельца
--- цикл жизни ---
[каждый раз]  ЗАПУСК          -> веса в память, Φ открыта
[каждый раз]  ПРОБУЖДЕНИЕ     -> запись в Φ о разрыве (узел I)
[каждая реплика] ХОД          -> чтение памяти -> ответ -> акты -> запись -> подтверждение
[постоянно]   ПОПОЛНЕНИЕ Φ1   -> всякое воспринятое оставляет след
[постоянно]   ЗАТУХАНИЕ       -> вычисляется при обращении, не пишется
[закрытие]    ЗАВЕРШЕНИЕ      -> НИЧЕГО не делается: всё уже на диске (узел H)
[сбой питания] ВОЗОБНОВЛЕНИЕ  -> проверка целостности, откат незавершённой записи
```

### 3.2. Процесс 1. ЗАПУСК

| Что | Описание |
|---|---|
| **Кто** | код изделия |
| **Когда** | пользователь запустил |
| **Вход** | файл `A = (K, Φ)` |
| **Шаги** | 1) открыть файл; 2) прочитать шапку весов, найти смещение Φ; 3) прочитать шапку Φ (ручки, счётчики, тик, версия формата); 4) **проверить версию формата**; 5) загрузить веса в память; 6) **открыть Φ на запись с блокировкой** |
| **Выход** | веса в памяти, Φ открыта на чтение и запись |
| **На диске после** | без изменений |
| **Сбои** | файл повреждён → отказ; версия формата не совпала → отказ с указанием; нет места → предупреждение |
| **Проверка** | файл 8,20 ГБ грузится; шапка читается; версия формата названа |

**Чего сегодня нет:** проверки версии формата; блокировки файла.

### 3.3. Процесс 2. ПРОБУЖДЕНИЕ (новый узел I)

| Что | Описание |
|---|---|
| **Кто** | код изделия |
| **Когда** | сразу после запуска |
| **Вход** | тик в шапке Φ, время последней записи |
| **Шаги** | 1) сравнить тик в шапке с максимумом тиков записей; 2) если между сессиями прошло время — **записать в Φ след разрыва**; 3) увеличить счётчик пробуждений |
| **Выход** | запись-событие в Φ: «был перерыв» |
| **На диске после** | +1 запись, тик +1 |
| **Сбои** | системные часы переставлены → записать как есть, пометить |
| **Проверка** | между двумя запусками в Φ появляется запись о разрыве |

**Чего сегодня нет:** целиком.

**Почему это важно.** Канон: «спячка — ноль прожитого времени; пробуждение — записываемое событие». Без этого модель не отличает «продолжение разговора» от «после долгого перерыва».

### 3.4. Процесс 3. ХОД (реплика)

**Самый важный процесс.** Разбит на шаги.

| # | Шаг | Кто | Что на диске |
|---|---|---|---|
| 1 | **Пополнение Φ1** — воспринятое (вопрос, ответ) | физика | +записи Φ1 |
| 2 | **Сборка восприятия** — что войдёт в ход | код | без изменений |
| 3 | **Подача** — векторы записей + вопрос | код | без изменений |
| 4 | **Ответ модели** | модель | без изменений |
| 5 | **Разбор актов** | код | без изменений |
| 6 | **Исполнение актов** | код | **+записи Φ2, +тик** |
| 7 | **Сброс на диск** | код | **записи гарантированно на диске** |
| 8 | **Подтверждение модели** | код | без изменений |

**Ключевое: шаг 7 обязателен.** Без него шаги 1–6 могут остаться в кеше системы и исчезнуть при выключении.

### 3.5. Процесс 4. ЗАТУХАНИЕ

| Что | Описание |
|---|---|
| **Кто** | код, при обращении к записи |
| **Когда** | при отборе для показа и при чтении |
| **Как** | `громкость = (1+повторы) · exp(−(тик − тик_записи)/τ_слоя)` |
| **Пишется ли в файл** | **НЕТ** — вычисляется. Хранится начальная амплитуда и тик |
| **Почему так** | тогда файл верен в любой момент; «дописать при выключении» не существует |
| **Проверка** | старая запись даёт меньшее число, чем свежая с тем же содержанием |

**Требует решения 1 (закон).**

### 3.6. Процесс 5. ПОПОЛНЕНИЕ Φ1 (восприятие)

| Что | Описание |
|---|---|
| **Кто** | код (физика) |
| **Когда** | на каждом ходу: вопрос и собственный ответ |
| **Условие** | порог захвата: мера неожиданности выше порога (перплексия) |
| **Куда** | регион Φ1 |
| **Размер** | 87 % памяти, 1 296 111 мест |
| **Проверка** | после хода в Φ1 появились записи; они видны модели через `scan` |

**Требует решения 3.**

### 3.7. Процесс 6. ЗАВЕРШЕНИЕ (выключение)

| Что | Описание |
|---|---|
| **Кто** | никто |
| **Когда** | пользователь закрыл программу или выключил компьютер |
| **Что делать** | **НИЧЕГО.** Всё уже на диске (шаг 7 процесса 3) |
| **Почему** | если нужно «дописать при закрытии», значит процессы 3 и 5 устроены неверно |
| **Проверка** | выключить питание в любой момент → при следующем запуске ничего не потеряно, кроме текущей недописанной реплики |

**Это новый узел H. Его сегодня нет.**

### 3.8. Процесс 7. ВОЗОБНОВЛЕНИЕ после сбоя

| Что | Описание |
|---|---|
| **Когда** | при запуске, если найдена незавершённая запись |
| **Как** | каждая запись пишется с признаком завершённости; незавершённая отбрасывается |
| **На диске** | откат к последней целой записи |
| **Проверка** | выключить питание во время записи → файл читается, откат сделан |

### 3.9. Процесс 8. ВЫТЕСНЕНИЕ (Φ заполнен)

| Что | Описание |
|---|---|
| **Когда** | места не осталось |
| **Как** | затирается **самая тихая** запись (по вычисленной громкости), не самая старая |
| **Почему так** | затухание — условие обобщения: слабый след и должен уйти первым |
| **Проверка** | при заполнении уходит самая тихая; номера остальных записей **не меняются** |

**Сегодня вытеснение ломает нумерацию — дефект.**

### 3.10. Процесс 9. ЧТЕНИЕ (акт `read`)

| Вид | Что должно быть | Сегодня |
|---|---|---|
| `last` | N **последних** (по замыслу) или самых громких | отдаёт **самые старые** — дефект |
| `ids` | ровно названные | работает |
| `from/to` | по **времени** (valid_time) | фильтрует по **номеру** — дефект |
| `scan` | числа физики | работает |

### 3.11. Процесс 10. СБОРКА (однократно)

| # | Шаг | Проверка |
|---|---|---|
| 1 | Проверка исходников | ядро грузится, материал цел |
| 2 | Сборка материала | три слоя, доли, уникальность |
| 3 | Проход Инструкции (LoRA) | loss падает, модель не деградирует |
| 4 | Слияние адаптера | файл грузится, отвечает |
| 5 | Создание Φ | смещение верно, ёмкость верна |
| 6 | Запись кода в изделие | **версия формата в шапке** |
| 7 | Обкатка | акты, память, тик, перезапуск |
| 8 | Передача | паспорт полон |

## 4. Порядок работ

### 4.1. Сначала — то, что не требует решений

| # | Работа | Почему |
|---|---|---|
| 1 | `read last` — отдавать последние | модель училась одному, получает обратное |
| 2 | `read from/to` — по времени | по инструкции это период |
| 3 | Молчаливый дефолт слоя → отказ | нарушение C4 |
| 4 | `layer_taken` → номер слоя, не индекс | одно поле, два смысла |
| 5 | Вытеснение → не ломать нумерацию | `read ids` возвращает не то |
| 6 | Сброс на диск после каждой записи | иначе выключение теряет |
| 7 | Версия формата в шапку | иначе нельзя менять формат |
| 8 | Ложная выдача объектива на слое 48 | замеры содержат артефакт |
| 9 | Подключить `vector.py` вместо заглушки | иначе в Φ шум |
| 10 | Убрать второй файл: текст внутрь Φ | нарушение «один файл» |

### 4.2. После решений — узлы

| Узел | Что | Зависит от |
|---|---|---|
| C | Снятие вектора с ядра | — (код готов) |
| D | Амплитуды | — (код готов) |
| E | Затухание | **решение 1** |
| F | Подача вектором | C, D |

### 4.3. Порядок узлов

**C → D → E → F** (цепочка: вектор, амплитуда, старение, подача). Параллельно **H** и **I** — они не зависят от физики.
**Φ1** — после F: сначала убедиться, что Φ2 работает.

## 5. Проверки узлов

| Узел | Проверка | Как |
|---|---|---|
| C | вектор = состояние ядра | сравнить с шумом: коды не совпадают с заглушкой |
| D | амплитуды из состояния | не константа `[1,1,1,1,1]` |
| E | старая запись тише | одна запись, разные тики записи |
| F | **ответ меняется от подачи** | подать вектор → ответ содержит знание, которого нет в тексте |
| H | выключение безопасно | выключить питание → ничего не потеряно |
| I | разрыв записан | два запуска → запись о перерыве |
| Φ1 | восприятие пишется | после хода в Φ1 есть записи |

**Узел F — главная проверка изделия.** Если ответ не меняется от подачи вектора, изделия нет.

## 6. Честная граница

**Чего план не решает:**

- **Каким будет поведение на машинах без Apple.** Библиотека mlx работает только на M-чипах. Это отдельный вопрос, в плане его нет.
- **Как изделие запускает пользователь.** Сейчас — командной строкой. Обёртка не входит в этот план.
- **Сколько живёт экземпляр.** Канон: «пока существует файл» (О-7). Резервное копирование — вне проекта.

**Чего не знаю:**

- сработает ли подача вектора (узел F не проверен);
- достаточно ли порога захвата для Φ1 (числа предварительные);
- как поведёт себя запись на диск при интенсивной работе.

**Что обязуюсь:**

- не начинать сборку до решений раздела 2;
- не называть узел закрытым без проверки из раздела 5;
- докладывать по узлам, а не по работам.
